# ADR-0003: MCP サーバーは `image-forge mcp` サブコマンドとして置く（ファイル渡し・非同期ジョブ）

- Status: Accepted
- Date: 2026-07-07

## Context

image-forge は CLI から扱いやすい。これを AI が画像生成ツールとして使えるようにするため、
Model Context Protocol (MCP) サーバーを追加する。本 ADR を駆動した設計上の問いは 2 つ:
**サーバーをどこに置くか**、そして **画像をどう返すか**。

util-series には既に MCP サーバーがある — `voice-studio-mcp`・`video-studio-mcp`・
`data-toolbox-mcp` — いずれも独立プロジェクトで、JSON-RPC 2.0 を stdio 上に手書きし
（外部 MCP ライブラリは使わない）、*外部*エンジンを子プロセスとして駆動する
（AivisSpeech、ffmpeg、Podman コンテナ）。これらは **ファイル渡し**である: エージェントは
ワークスペースディレクトリで作業し、ツールはメディアのバイト列ではなくファイルの*パス*を
返し、長い処理は **非同期ジョブ**として走る（`master` → `job_id`、`check_job` でポーリング）。

image-forge は 1 点で決定的に違う。その diffusion エンジン（stable-diffusion.cpp + ggml +
Metal）は外部プロセスではなく、**バイナリへ静的リンクされている**（ADR-0001）。

## Decision

**MCP サーバーは既存バイナリの `image-forge mcp` サブコマンドとして出荷し、作業とファイルの
受け渡しについては studio 群のファイル渡し + 非同期ジョブ契約をそのまま写す。**

配置 — **独立プロジェクトではなくサブコマンド**:

- エンジンは既にバイナリの中にある。独立した `image-forge-mcp` は、重い CGO/Metal
  エンジンを再リンクする（署名・notarize 対象となる、遅い darwin/arm64 専用ビルドが
  2 本目になる）か、`image-forge serve` を子プロセスとして駆動する（利点なしにプロセス
  境界が 1 つ増える）かのどちらかになる。バイナリ内であれば MCP ワーカーは
  **常駐エンジンセッション**を直接再利用でき — `serve` と同じ、一度ロードしてモデル変更時に
  再ロードする機構 — レジストリ・config・プロファイルも共有する。
- util-series の「単一バイナリ + サブコマンド」規約に合う。studio 群が独立しているのは
  エンジンが外部にあるからで、その理由はここには当てはまらない。

ファイルの受け渡し — **studio 群を写す**:

- **ワークスペースモデル。** 1 ワークスペース = 1 作業ディレクトリ（データディレクトリ配下の
  既定ルート、または呼び出しごとにエージェントが用意する `workspace_root`）。サーバーが
  書くのは `<ws>/output/` 配下のみ。入力画像（img2img/inpaint）はエージェントが置き、
  ワークスペース相対パスで参照し、`os.Root` 経由で解決するので、仕込まれた symlink では
  ワークスペースの外へ出られない。
- **バイト列ではなくパス。** `generate` は `output/` 配下に PNG を書き、そのパスを返す。
  画像のバイト列はプロトコル上を流れない。
- **非同期ジョブ。** `generate` はジョブを投入して `job_id` を返す。単一ワーカーが常駐
  セッションに対してジョブを FIFO で処理する（Metal エンジンは並行安全でない）。
  `check_job` が状態・進捗・出力パスをポーリングする。これにより 1〜2 分かかる描画で
  クライアント側のツール呼び出しタイムアウトを回避できる。
- **構造化されたツールエラー** `{code, message, details}` と、ワークスペースモデル・
  `generate` のスキーマ・ジョブのライフサイクル・リカバリ表を記述する **`get_usage`**
  ツール。

ツール (v1): `get_usage`・`generate`・`check_job`・`list_models`。モデル管理
（`pull`/`quantize`）は CLI 専用のままにする — 数 GB のダウンロードと NSFW のオプトインは
AI のツール呼び出しには馴染まない。

## Consequences

- バイナリ 1 つ、署名/notarization フロー 1 つ。重いエンジンの 2 本目のビルドは要らない。
- AI はワークスペースへ生成し、AI（または利用者）が使えるファイルパスを得る。常駐
  セッションはジョブを跨いでモデルを温めたままにする。
- トランスポートは当面 stdio のみ。Streamable HTTP は後続候補。
- JSON-RPC / MCP のプロトコル層・ワークスペース封じ込め・ジョブマネージャは
  `video-studio-mcp`（実績あり）から移植し、image-forge の「追加依存ゼロ」姿勢
  （stdlib + BurntSushi/toml）を保つ。
