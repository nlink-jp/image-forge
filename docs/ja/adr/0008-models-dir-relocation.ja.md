# ADR-0008: 移動した `models_dir` とレジストリを突き合わせる

- Status: Accepted
- Date: 2026-08-02

## Context

`config.toml` の `models_dir` は **pull したモデルファイルの書き込み先**を移す
（起動時の `store.SetModelsDir`、読み出しは `store.ModelsDir()`）。対してレジストリは
**重みファイルごとの絶対パス**を記録する — `path`・`vae_path`・`components` の各
フィールドである。この 2 つの事実はどこでも突き合わされない。

そのため、利用者がモデルを大きなディスクへ移す普通のやり方 —

1. `~/.local/share/image-forge/models/*`（あるいは旧 `models_dir`）を新しいボリュームへ
   移動し、
2. `models_dir` を新しい場所に向ける、

— は、インストール済みモデル全部のレジストリパスを、もう存在しないディレクトリへ向けた
ままにする。`config.go` はこれを記述している（「既にインストール済みのモデルはレジストリに
記録された絶対パスを保つ」）が、それに対して何も手を打っていない。

この失敗は、最も悪い場所で無言である。`installedViews` はレジストリからそのまま行を組み、
**ファイルを一切 stat しない**ので、`models list`・`models list --json`・MCP の
`list_models` ツール・GUI の Manage Models ウィンドウは揃ってモデルをインストール済みで
健全だと報告する。ファイルシステムに触る最初のコードは `gen` / `serve` であり、そこで
古いディレクトリを名指したロードエラーになって落ちる。利用者から見た事象は「モデル
マネージャは私のモデルを見えているのに、生成は古いパスだと言う」になる — ツールが、
確認していない状態を断定したのである。

別個の欠陥が 2 つある:

- **パスの突き合わせが無い。** models dir が動いたときレジストリを書き換えるものが無く、
  それを依頼するコマンドも無い。
- **存在確認が無い。** どの一覧表示の面も、未検証の状態を事実として提示している。

第 3 のシナリオが同じ形と同じ修正を共有する: 外付けボリューム上の `models_dir` が単に
マウントされていない場合である。ファイルは「消えた」わけではないが、一覧はそれが
そこにあると主張してはならない。

## Decision

**明示的な `models relocate` コマンドを追加し、すべての一覧表示の面が重みファイルの欠落を
報告するようにする。** 突き合わせは利用者が起動し、事前に内容を確認できる操作である —
暗黙の修復ではない。

1. **ファイルフィールドの走査は `store` が所有する。** `InstalledModel` が `fileRefs()` を
   持つようになり、記録された重みファイルのフィールド（`path`・`vae_path`・
   `components.*`）ごとに get/set アクセサをフィールド名付きで返す。インストール済み
   モデルのファイルを列挙または書き換える必要のある利用者はすべてこれを通るので、新しい
   コンポーネントフィールドが、ある呼び出し側では見落とされ別の呼び出し側では尊重される、
   ということが起こり得なくなる。この上に構築するもの:
   - `InstalledModel.MissingFiles(exists)` — `exists` が拒否した記録済みファイル。
   - `Registry.Relocate(dir, apply, exists)` — 計画/適用のコア。

   `exists` は（`os.Stat` ではなく）注入される。これにより両者が合成ファイルシステムに
   対してユニットテスト可能になる。テスト容易性の規則どおりである。

2. **relocate が rebase するのは壊れているものだけ、しかもベース名でだけ。** ファイルが
   `<dir>/<basename>` に書き換えられるのは、記録されたパスが存在せず**かつ**その候補が
   存在する**とき限り**である。まだ解決するパスには決して触れない — 意図的にモデルを複数
   ディレクトリへ散らしている利用者はそれを保つ。対象ディレクトリに候補が無い欠落ファイルは
   未解決として報告され、推測はしない。

3. **既定は dry-run、`--apply` で書く。** `models relocate` は計画を表示して終了する。
   `models relocate --apply` がレジストリを書き換える。これは `models gc` の
   「まず報告、次にオプトイン」の形に倣っている。対象は `store.ModelsDir()`（つまり設定
   された `models_dir`）で、`--to <dir>` がそれを上書きする。これは同時に、この操作自身の
   undo にもなる — `--to <old-dir>` で再実行すればよい。

4. **一覧が欠落ファイルを報告する。** `installedView` が `missing_files []string` を持つ
   ようになり（空なら省略）、レジストリのパスを stat して埋める。`models list` の表に
   **`STATUS`** 列が加わり、健全なモデルでは空欄、壊れたモデルでは `MISSING` になる。
   加えて、欠けているファイルを名指しし `models relocate` を指し示すフッタが付く。
   `ListModels` が CLI・`--json`・MCP の単一の供給元なので、3 つ同時にこれを得る。

5. **GUI はこれを見せ、描画を拒否する。** `ModelInfo` が `missing_files` をデコードし、
   Manage Models はその行に印を付け、Composer は欠落ファイルを持つモデルをピッカーから
   外し、実行可能な案内とともに生成をブロックする。モデルを利用可能として見せる
   フロントエンドは、それをロードできなければならない。

### 却下: レジストリのロード時に暗黙で rebase する

`store.Load()` が、存在しないパスを黙って `<models_dir>/<basename>` に差し替えることも
できた。利用者の操作なしで config 編集が「ただ動く」ようになる — しかしそれは、利用者が
たったいま変更したディレクトリに対してベース名で解決するので、無関係な同名ファイルが
一言もなくロードされ得るし、ディスク上のレジストリはプロセスが実際に使ったものと食い違い
続ける。目に見えず自己修復する状態は、自分の壊れを報告する状態より推論が難しい。明示的な
コマンドと誠実な一覧表示を採り、これを却下した。

### 対象外

- **ファイルの移動。** `relocate` はレジストリを書き換えるだけで、重みをコピーも削除も
  しない。バイト列を動かすのは利用者の手順（`mv`）であり、その前に `--dry-run` すれば
  すべてが未解決として正しく報告される。
- **config 変更の監視。** `config.toml` の編集に対して突き合わせを行うデーモンは無い。
- **モデル単位の relocate。** レジストリ全体を一度に突き合わせる。1 モデルだけ差し替え
  たいという要望を示すものは今のところ何も無い。

## Consequences

- モデルを別のディスクへ移す作業が次の形になる: ファイルを `mv` し、`models_dir` を編集し、
  `image-forge models relocate --apply` を実行する。明示的な 3 手順、それぞれ検証可能である。
- 重みが存在しないモデル — relocate されたディレクトリ、未マウントのボリューム、
  image-forge の外で削除されたファイル — は、古いパスでロード時に失敗するのではなく、
  一覧されるあらゆる場所で `MISSING` と報告される。
- `models list` は呼び出しごとに `O(files)` 回の stat を行う。欠落/未マウントのパスでは
  これらは即座に失敗する（ENOENT）ので、コストは有界であり、退化ケースが最速のケースに
  なる。
- `fileRefs()` が `rm --purge`・`gc`・`MissingFiles`・`Relocate` に「このモデルが所有する
  ファイル」の単一の定義を与える。`Files()` は今それを用いて表現されている。
- `InstalledModel` に重みファイルのフィールドを追加するとき、更新が必要なのは
  `fileRefs()` だけである。
